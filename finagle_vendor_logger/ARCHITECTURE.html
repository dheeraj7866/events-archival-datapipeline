§03 — Fan-In / Fan-Out Patterns

🔀
Fan-In — 3 producers → 1 SQS queue
Service topology convergence
  • identity-api, los-api, payment-api all enqueue to the same SQS queue
  • Each service runs its own in-process ring buffer — no cross-service coupling
  • SQS acts as the single durable convergence point (message persistence, at-least-once delivery)
  • Standard queue (not FIFO) — order not guaranteed, which is acceptable for compliance logging
  • service field in every event identifies the producer for Grafana filtering
Producer isolation: if identity-api is down, los-api and payment-api still independently drain to SQS. No shared in-process state.
📤
Fan-Out — 1 Lambda → 2 sinks
S3-first write ordering
  • Lambda reads SQS batch, writes to S3 first (PutObject + Legal Hold)
  • ClickHouse INSERT is second — uses S3 keys as evidence pointers
  • If ClickHouse is down: S3 is the truth. Athena can query the evidence directly
  • If S3 write fails: Lambda throws, message returns to SQS queue (visibility timeout)
  • Fan-out is ordered by criticality, not parallel — compliance evidence before index
S3 Object Lock COMPLIANCE makes objects permanently immutable — even root cannot delete. Legal Hold requires compliance-officer IAM role + MFA (D7 pending).
🔌
Sidecar / Plug-and-Play
Zero-coupling library design
  • VendorLoggerModule.forRoot(opts) is a NestJS dynamic module — installed in one import line
  • No changes to existing vendor service code — only wrap calls in vendorHttp.call()
  • Fail-open guarantee: logger errors never break the vendor call chain
  • Ring buffer is in-process — no sidecar process or daemon needed
  • Library is framework-version-agnostic (NestJS v10 + v11 via peer-dep range)
Upgrading the library does not require changes to the host service's business logic — only the module registration config.

§04 — Code Review Findings

Reviewed against production-safety, RBI compliance, and the NFRs in the TDD. Severity: BUG = must fix before prod · IMPROVE = should fix before prod · DESIGN = discussion / phase 2

BUG · HIGH

SqsDrainService — events permanently lost on SQS partial failure

drainOnce() calls buffer.drain(100) BEFORE sending to SQS. If sendBatches() throws (network error, SQS throttle), those 100 events are already removed from the ring buffer — they're gone. The Failed array in the batch response is logged but not re-queued either. This silently drops compliance events, violating the RBI retention guarantee.

FIX — re-enqueue on failure
private async drainOnce(): Promise<void> {
  if (this.draining || this.buffer.size === 0) return;
  this.draining = true;
  const events = this.buffer.drain(MAX_DRAIN_PER_TICK);
  try {
    await this.sendBatches(events);
  } catch (err) {
    // Re-enqueue so events aren't lost on transient SQS failure
    for (const e of events) this.buffer.push(e);
    this.logger.error('SQS drain failed — re-enqueued events', err);
  } finally {
    this.draining = false;
  }
}

Also handle result.Failed: re-enqueue those specific events only.

BUG · MEDIUM

requestHash computed post-truncation — breaks audit integrity

In buildEvent(), requestHash = pii.hashPayload(reqStr) is computed after serializePayloads() which may truncate reqStr. This means the stored hash is of the truncated string, not the original vendor request. An RBI auditor cannot verify the original payload using this hash — it's a broken chain of custody.

FIX — hash the original, flag truncation separately
// In serializePayloads(), return the original before truncation
const originalReqStr = JSON.stringify(req) ?? '';
const requestHash = pii.hashPayload(originalReqStr);  // ← hash of FULL payload
// then truncate for storage
const reqStr = truncate(originalReqStr, maxBytes);
return { reqStr, resStr, truncated, requestHash };
IMPROVE · HIGH

No per-message SQS size guard — single event could exceed 256KB SQS limit

SQS hard limit is 256KB per message body. The 128KB payload truncation per field helps, but the full event JSON includes many other fields. A ClickHouse errorMessage containing a large stack trace, combined with both payloads near 128KB, could produce a >256KB message — which SQS silently rejects.

FIX — add message-level size check in sendBatches()
const SQS_MAX_MSG_BYTES = 256 * 1024;

entries.map(e => {
  if (Buffer.byteLength(e.MessageBody, 'utf8') > SQS_MAX_MSG_BYTES) {
    // fallback: strip payloads, keep metadata
    const small = { ...JSON.parse(e.MessageBody),
      requestPayload: '[OVERSIZED]', responsePayload: '[OVERSIZED]', payloadTruncated: true };
    e.MessageBody = JSON.stringify(small);
  }
  return e;
});
IMPROVE · MEDIUM

Metrics http_status label causes cardinality explosion

http_status: String(httpStatus) in the Counter label creates a unique time series per distinct HTTP status code per vendor per endpoint. With Karza returning custom error codes like 422, 429, 403, 409, 499, this multiplies time series count fast. Prometheus recommends max ~10 values per label.

FIX — normalize to bands
function statusBand(code: number): string {
  if (code === 0)   return 'no_response';
  if (code < 200) return '1xx';
  if (code < 300) return '2xx';
  if (code < 400) return '3xx';
  if (code < 500) return '4xx';
  return '5xx';
}
// in recordCall():
this.callCounter.inc({ ...base, http_status: statusBand(httpStatus) });
IMPROVE · MEDIUM

enqueue() warning message has wrong capacity display

The warn log says capacity=${this.buffer.size} but buffer.size returns the current count of items, not the capacity. When full, they're equal — but the message is semantically wrong. Add a capacity getter to RingBuffer.

FIX
// In RingBuffer:
get capacity(): number { return this.capacity_; }

// In enqueue():
`Ring buffer full (size=${this.buffer.capacity}) — oldest event dropped`
DESIGN

Lambda mapping gap — s3_request_key and s3_response_key not in VendorApiEvent

The ClickHouse schema has s3_request_key and s3_response_key columns (the S3 object path for each payload). These are generated by Lambda after the S3 write. There is currently no documented mapping of how Lambda transforms a VendorApiEvent (SQS message) into a ClickHouse row including these columns. The Lambda code doesn't exist yet — this needs to be specced before Lambda implementation.

S3 KEY CONVENTION (proposed)

DESIGN

No dead-letter queue (DLQ) alarm on the SQS queue

If Lambda consistently fails to process a message (malformed event, schema mismatch), it will retry until the visibility timeout expires, consuming concurrency slots and delaying real events. A DLQ with CloudWatch alarm on ApproximateNumberOfMessagesVisible > 0 is needed. This is infra-level, not library-level — but needs to be in the Terraform module.

§05 — ClickHouse Connection (Lambda → ClickHouse)

The library itself never connects to ClickHouse. The Lambda consumer reads SQS, writes S3, then INSERTs into ClickHouse via HTTP.

Connection design

1

Client: @clickhouse/client (official)

HTTP interface on port 8123 — stateless, perfect for Lambda. No TCP connection pooling needed. Uses KeepAlive internally for same-invocation batches.

2

async_insert mode

async_insert=1, wait_for_async_insert=0 — Lambda fires INSERT and returns. ClickHouse buffers and flushes to MergeTree. Reduces Lambda duration cost, acceptable for compliance (not OLTP).

3

VPC internal — no public endpoint

Lambda and ClickHouse EC2 are in the same private subnet. Connection string: http://10.0.x.x:8123 (private IP or Route53 private hosted zone).

4

Auth: username + password from Secrets Manager

ClickHouse user vendor_archive_writer with INSERT-only permission on vendor_archive.vendor_api_events. Credentials in Secrets Manager, fetched at Lambda cold start.

5

S3 keys added by Lambda (not library)

Lambda generates s3_request_key / s3_response_key after writing to S3. These are appended to the event before ClickHouse INSERT.

Lambda skeleton code

// lambda/vendor-archive-ingest/index.ts
import { createClient } from '@clickhouse/client';
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';
import { SQSHandler, SQSRecord } from 'aws-lambda';
import { VendorApiEvent } from '@finagle/vendor-logger';
import { compress } from '@aws-sdk/util-gzip';

// Cold-start singletons
const s3 = new S3Client({ region: 'ap-south-1' });
const ch = createClient({
  url: process.env.CLICKHOUSE_URL,      // http://10.0.x.x:8123
  username: process.env.CH_USER,
  password: process.env.CH_PASSWORD,
  database: 'vendor_archive',
  clickhouse_settings: {
    async_insert: 1,
    wait_for_async_insert: 0,
  },
});

export const handler: SQSHandler = async (sqsEvent) => {
  const rows: ClickHouseRow[] = [];

  for (const record of sqsEvent.Records) {
    const event: VendorApiEvent = JSON.parse(record.body);
    const dateStr = event.createdAt.substring(0, 10);
    const base = `vendor_id=${event.vendorId}/event_date=${dateStr}/request_id=${event.requestId}`;

    // ① S3 FIRST — compliance evidence
    const s3RequestKey = `${base}/request.json.zst`;
    const s3ResponseKey = `${base}/response.json.zst`;

    await s3.send(new PutObjectCommand({
      Bucket: process.env.ARCHIVE_BUCKET,
      Key: s3RequestKey,
      Body: await compress(event.requestPayload),
      ContentEncoding: 'gzip',
      ContentType: 'application/json',
      ObjectLockMode: 'COMPLIANCE',
    }));

    // KMS encrypt aadhaar last4 (via Secrets Manager CMK)
    const aadhaarEncrypted = event.aadhaarLast4Hash
      ? await kmsEncrypt(event.aadhaarLast4Hash)
      : undefined;

    rows.push(toClickHouseRow(event, s3RequestKey, s3ResponseKey, aadhaarEncrypted));
  }

  // ② ClickHouse SECOND — hot index
  await ch.insert({
    table: 'vendor_api_events',
    values: rows,
    format: 'JSONEachRow',
  });
};
